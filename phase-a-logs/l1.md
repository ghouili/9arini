Fix:
- **`apps/api/src/lib/thread-state.ts` → `threadState(threadId): Promise<ThreadState>`.** This is the one decision, a single query on the server clock. The reasons, in order:
  - `closed:blocked`: `profiles.blocked_at` on either side, or `tutors.suspended_at`, which is set with a block and on erasure;
  - `closed:consent-withdrawn`: a withdrawn consent (0023) and none standing;
  - `closed:booking-cancelled`: the existing rule;
  - `closed:class-ended`: `scheduled_at + coalesce(duration_min, 90) min + THREAD_CLOSE_DAYS days <= now()`.
- **Send** uses it. `booking-cancelled` keeps its old error code, because `e2e/security-access.spec.ts` asserts it exactly. Every other reason answers **`{ ok:false, error:"thread-closed" }`**.
- **Payloads.** `MessageThreadDetail.state` (participant and guardian views) is filtered by `shownThreadState()`, so consent-withdrawn and blocked read as a plain `"closed"`. The tutor is never told why, which matches `guardian.ts` ("told a seat came free, never why"), and nobody learns of a block.
- **UI.**
  - `messages/[id]`: an FR/AR closed banner (`data-testid="thread-closed"`), and the textarea and send button are disabled. On a `thread-closed` or `booking-cancelled` error the page reloads so the banner appears.
  - `guardian/threads/[id]`: an FR/AR closed banner only.
  - `e2e/thread-closed.spec.ts` (written, not run).
- Reading and reporting do not consult the state.

**Consent withdrawal, as read:** `consents.withdrawn_at` (0023) is set by `POST /guardian/children/:id/consent/withdraw` (`routes/guardian.ts`). `misc.ts` `POST /consent` refuses to undo it (`consent-withdrawn`). `misc.ts` was read, not edited. The gap was **past** classes: withdrawal releases only upcoming seats, so a past class's thread stayed writable.
