## Migration 0025_birth_month.sql — written here BEFORE it was applied

```sql
BEGIN;

ALTER TABLE "profiles" ADD COLUMN IF NOT EXISTS "birth_month" integer;

DO $$
BEGIN
  ALTER TABLE "profiles"
    ADD CONSTRAINT "profiles_birth_month_range"
    CHECK ("birth_month" IS NULL OR ("birth_month" BETWEEN 1 AND 12));
EXCEPTION WHEN duplicate_object THEN NULL;
END $$;

DO $$
BEGIN
  ALTER TABLE "profiles"
    ADD CONSTRAINT "profiles_purged_has_no_birth_month"
    CHECK ("purged_at" IS NULL OR "birth_month" IS NULL);
EXCEPTION WHEN duplicate_object THEN NULL;
END $$;

COMMIT;
-- ROLLBACK (manual):
--   ALTER TABLE "profiles" DROP CONSTRAINT IF EXISTS "profiles_purged_has_no_birth_month";
--   ALTER TABLE "profiles" DROP CONSTRAINT IF EXISTS "profiles_birth_month_range";
--   ALTER TABLE "profiles" DROP COLUMN IF EXISTS "birth_month";
```

**How existing rows are kept.** The column is added nullable, with no default and no back-fill. Every existing profile keeps
exactly what it had (`birth_year` untouched) and gets `birth_month = NULL`. `isAdult()` treats a NULL month as a minor, which
is the fail-safe direction D6 asks for. Nothing is rewritten or dropped. Both CHECKs hold for every existing row, because the
new column is NULL everywhere. The second CHECK carries 0022's "an erased account has no identity" promise over to the new
column, as a separate constraint, so 0022's constraint is not touched. A student whose month is unknown can give it once at
sign-in on `/signup/eleve`: verify fills an UNKNOWN month only, and only for the birth year already on file. The
student → tutor upgrade asks for a missing month the same way.

## A24 · finding D6 (+ report §2 "code link skips the birth year", §3 "year-only minor check") · commit `79a2256`

**What changed.** `packages/shared/src/age.ts` (new): `vBirthMonth`, `isAdult(birthYear, birthMonth, now)`, `minorsAllowed()`.
`isAdult` counts the months since the birth month in **Africa/Tunis** (`tunisWallTime`). It returns adult only when the 18th
birthday fell in a month that is already over. In the birthday month itself the day is unknown, so the answer is "minor" until the
1st of the next month. A missing or implausible month or year counts as a minor. `minorsAllowed()` reads
`process.env.ALLOW_MINORS === "1"` on every call. The API changes:
- `POST /auth/otp/verify` needs `birthYear` + `birthMonth` to create a student account (`birth-date-required`). While minors are
  off, it refuses a minor (`adults-only`). The check runs after the code is proven, like the existing `no-account` branch, so it
  covers the "J'ai déjà un code" path too, which never calls `/otp/request`. An existing minor account still signs in.
  `needsConsent` is now month-aware.
- `POST /bookings`: one self-contained insertion next to the consent check. While minors are off, a non-adult gets `adults-only`.
  When they are on, a month-aware consent check runs, because the year-only check below it let a 17-year-old born later in the
  year book without consent. The existing check is unchanged.
- `session.ts` selects `birthMonth`; `guardian.ts` computes `isMinor` month-aware.
- Web: `SignupInner` has month + year selects, checks them before a code is spent (on send AND on "J'ai déjà un code"), and
  shows the refusal on the field in FR and Derija. `AuthInner` reads **"Je suis élève"** while minors are off and "Je suis élève /
  parent" only when on. Both server shells read `minorsAllowed()` per request. Checkout shows an `adults-only` message.
- The guardian/consent code is intact. With `ALLOW_MINORS=1` a minor still books only with consent (test below).
