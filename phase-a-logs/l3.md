### Migration `packages/db/sql/0026_cancellation_ledger_rekey.sql` (written here before it was applied)
```sql
ALTER TABLE "cancellations" DROP CONSTRAINT IF EXISTS "cancellations_booking_id_unique";
-- In case a database ever carried it as a bare unique index rather than a constraint.
DROP INDEX IF EXISTS "cancellations_booking_id_unique";

CREATE UNIQUE INDEX IF NOT EXISTS "cancellations_booking_id_cancelled_at_unique"
  ON "cancellations" USING btree ("booking_id", "cancelled_at");
```
Rollback (manual; valid only while no booking has two ledger rows):
```sql
DROP INDEX IF EXISTS "cancellations_booking_id_cancelled_at_unique";
ALTER TABLE "cancellations" ADD CONSTRAINT "cancellations_booking_id_unique" UNIQUE ("booking_id");
```
**How existing rows are kept:** nothing is deleted, updated or rewritten. Every existing row already satisfies the new
index: the old unique allowed at most one row per `booking_id`, and NULL `booking_id`s (ledger rows whose booking was
erased, 0016) never collide in a unique index. The row's existing uuid PK `id` is the cancellation id;
`(booking_id, cancelled_at)` keeps the old guard against a double-write of ONE cancellation (`cancelled_at` defaults
to `now()`, the transaction start, so two inserts for one booking in one transaction still collide; two separate
cancellations never do). `booking_id` stays the leading column, so booking lookups remain index lookups.
**No `bookedAt` column:** reactivation resets `bookings.created_at = now()`, which is what the reschedule waiver
compares against; the tutor dashboard's "booked at" (the only other reader) then shows the current reservation.
Idempotent: `DROP … IF EXISTS` / `CREATE … IF NOT EXISTS`; `0009` is `CREATE TABLE IF NOT EXISTS`, so re-running
`db:sql` never re-adds the old unique on an existing table.
